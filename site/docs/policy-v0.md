# AKIOS policy language, version 0

**Status:** draft, 2026-09-29, for AKIOS 2.0. The loader (`src/akios/policy/load.py`), the enforcement matrix (`src/akios/policy/explain.py`), `akios policy validate | explain | test` and the enforcement of §5 are implemented. Version 0 may still change incompatibly until AKIOS 2.0.0 is released; after that, an incompatible change gets a new version number.

**Machine-readable schema:** [`src/akios/policy/schema/policy-v0.json`](https://github.com/akios-ai/akios/blob/main/src/akios/policy/schema/policy-v0.json) (JSON Schema 2020-12). It checks structure only; the rules of §4 and §6 apply on top of it.

**Examples:** [coding agent](https://github.com/akios-ai/akios/blob/main/docs/spec/examples/coding-agent.policy.yaml) · [Python script](https://github.com/akios-ai/akios/blob/main/docs/spec/examples/python-script.policy.yaml) · [LangChain application](https://github.com/akios-ai/akios/blob/main/docs/spec/examples/langchain-app.policy.yaml) · [coding agent on macOS](https://github.com/akios-ai/akios/blob/main/docs/spec/examples/coding-agent-macos.policy.yaml) · [Codex on macOS](https://github.com/akios-ai/akios/blob/main/docs/spec/examples/codex-macos.policy.yaml)

## 1. Purpose

A policy declares what one run of `akios run --policy <file> -- <command>` may do: which files the process and its descendants may read, write and execute, whether they may use the network, which environment variables they receive, what resources they may consume, and what the ledger records. The [threat model](/docs/threat-model.html) says what each clause protects against.

## 2. File format

- UTF-8 YAML or JSON. The document must map to the JSON data model: no YAML tags, no anchors, no duplicate keys.
- Numbers are integers. A fractional number is an error.
- An unknown key, at any level, is an error. A misspelt clause must never silently remove a restriction.
- Every clause except `version` is optional. An absent clause takes its default (§3).

## 3. Clauses

| Key | Type | Default | Meaning |
|---|---|---|---|
| `version` | `0` | required | Language version |
| `name`, `description` | string | none | Free text, recorded in the ledger |
| `filesystem.read` | list of paths | `[]` | Files and directories that may be read; a directory covers everything beneath it |
| `filesystem.write` | list of paths | `[]` | Files and directories that may be read, created, written, renamed and deleted |
| `filesystem.protect` | list of paths | `[]` | Files and directories kept read-only inside the `filesystem.write` directories: they may be read, not written, created, renamed or deleted (§4.5) |
| `exec` | `any` or list of paths | `any` | `any`: any readable file may be executed. A list: only files beneath these paths |
| `network` | `none`, `all`, `domains` | `none` | No network, unrestricted network, or (experimental) a domain allowlist |
| `network_domains` | list of host names | none | Only with `network: domains`. `*.example.org` covers subdomains |
| `environment.pass` | `all` or list of names | `[]` | Variables passed in addition to the base set (§5.4) |
| `resources.wall_seconds` | integer ≥ 1 | no limit | Wall-clock time of the run |
| `resources.cpu_seconds` | integer ≥ 1 | no limit | CPU time, per process |
| `resources.memory_mb` | integer ≥ 16 | no limit | Memory, in MiB |
| `resources.max_processes` | integer ≥ 1 | no limit | Processes and threads |
| `resources.file_size_mb` | integer ≥ 1 | no limit | Largest file the child may write, in MiB |
| `ledger.argv` | `redacted`, `none` | `redacted` | Record the command line after redaction, or not at all |
| `ledger.env_names` | boolean | `true` | Record the names, never the values, of the variables passed |
| `ledger.output_digests` | boolean | `false` | Record SHA-256 digests of stdout and stderr |
| `ledger.denials` | boolean | `true` | Record a summary of the operations the cage refused, where the host reports them (§5.6) |
| `on_unenforceable` | `refuse`, `degrade` | `refuse` | What to do when this host cannot enforce a clause (§6) |

## 4. Paths

1. A path is absolute (`/usr`), starts with `~` (the invoking user's home), `$TMPDIR` (the temporary directory: the value of `TMPDIR` in the environment of `akios`, or `/tmp` when it is unset or not an absolute path) or `$DEVELOPER_DIR` (on macOS, the developer tools the shims of `/usr/bin` load in the run, the folder `xcode-select -p` prints for it: the `DEVELOPER_DIR` of the environment of `akios` when the policy passes it, else the folder selected with `xcode-select --switch`, else the Command Line Tools; when there are none, and on another system, `/Library/Developer/CommandLineTools`, which then does not exist and grants nothing), or is relative to the directory that contains the policy file. `$TMPDIR` and `$DEVELOPER_DIR` are the only variables: a path that starts with another `$` is an error. `~user` and globs are not expanded; every other character is literal.
2. At run start, each path is resolved: `~`, `$TMPDIR` and `$DEVELOPER_DIR` expanded (`$DEVELOPER_DIR` looked up once per load, without running a program), relative paths joined, symbolic links followed. The resolved path is what is granted and what the ledger records, next to the declared one, in the effective policy (§8).
3. A path that does not exist at run start grants nothing. It is skipped and the skip is recorded; it is not an error.
4. **Reserved paths.** The ledger store (default `$XDG_STATE_HOME/akios`, that is `~/.local/state/akios`) and the key directory (default `$XDG_CONFIG_HOME/akios/keys`, that is `~/.config/akios/keys`) may not be granted. A policy in which any resolved path under `filesystem.read`, `filesystem.write` or `exec` is equal to, inside, or an ancestor of a reserved path is rejected. Granting `/`, `~` or `~/.config` is therefore always rejected, and so is granting the key file itself. Landlock cannot exclude a subdirectory from an allowed directory, so rejection is the only safe rule. On macOS the profile also denies the reserved paths after every grant (§5.7).
5. **Protected paths.** Each path of `filesystem.protect` must lie strictly inside a `filesystem.write` path (compared resolved, whether they exist or not); a protected path outside every write path, or equal to one, makes the policy invalid (a path outside the write paths is not writable already; a write path kept read-only belongs in `filesystem.read`). Protected paths resolve like the others (§4.1, §4.2), and `~` and `$TMPDIR` apply. A protected path that does not exist at run start is not skipped: on macOS it cannot be created; on Linux the clause is then unenforceable when an existing write path contains it (§5.1). A protected directory is protected with everything beneath it, and the folders that hold a protected path, where a write path would let them be renamed, stay in place, so it cannot be moved aside with them. For example, an agent that keeps its state and its configuration in the same folder:

   ```yaml
   filesystem:
     write: [~/.codex]                    # its state, sessions and logs
     protect:                             # what it runs or allows the next time it starts
       - ~/.codex/config.toml
       - ~/.codex/hooks.json
       - ~/.codex/rules
   ```

6. **Symbolic links to what must stay unchanged.** The policy file, and each path of `filesystem.protect`, must not be named through a symbolic link that lies inside a `filesystem.write` path: the cage keeps what the link leads to unchanged, not the link, which the program could replace so that the same name leads to another file the next time it is read. Such a policy is rejected, with the link and the write path named. A link outside the write paths is followed (§4.2): the file it leads to is the one protected, and the policy file is recorded by its resolved path (`source.path` of the effective policy, §8). For example, in a project granted for writing, `./akios.policy.yaml` that links to `conf/akios.policy.yaml` is rejected, and `--policy conf/akios.policy.yaml` is accepted.

## 5. Semantics and enforcement

The mechanisms are described in [threat model §5](/docs/threat-model.html#5-what-each-mechanism-enforces-linux) for Linux and [§5a](/docs/threat-model.html#5a-what-each-mechanism-enforces-macos) for macOS, where each property has a test. §5.1 to §5.3 describe Linux; §5.7 describes macOS, where one Seatbelt profile enforces `filesystem`, `exec`, `network` and the baseline. §5.4 to §5.6 apply to both.

### 5.1 `filesystem` and `exec` (Landlock)

- `read` grants reading files and listing directories. `write` grants, in addition, creating, writing, truncating, renaming, linking and deleting files and directories, and creating special files other than devices.
- `exec: any` grants execution beneath every `read` and `write` path. An `exec` list grants execution, and reading, beneath the listed paths only. Shared libraries and interpreters must be readable.
- Access to anything not granted is refused by the kernel with `EACCES` (FS-1 to FS-4).
- The clause is enforceable when Landlock is enabled and its ABI covers the rights the policy needs: ABI 1 (Linux 5.13) for everything above, ABI 2 (Linux 5.19) for renaming and linking into another directory, ABI 3 (Linux 6.2) for truncation. With a lower ABI, the affected rights are recorded as not enforced and the clause counts as unenforceable (§6). Since truncation applies to every writable file, the reference implementation requires ABI 3.
- Implementation (`src/akios/substrate/landlock.py`): the ruleset is built by the wrapper before the fork, one path-beneath rule per existing resolved path; the child sets `PR_SET_NO_NEW_PRIVS` and calls `landlock_restrict_self`. The handled rights are every filesystem right of the ABI except `IOCTL_DEV`. From ABI 6 the child is also scoped for signals, so it cannot signal the wrapper (PROC-2, K-PROC-02). On a path that is not a directory, only file rights are granted. The ELF interpreter of an executable (for example `/lib64/ld-linux-x86-64.so.2`) is opened by the kernel for execution, so with an `exec` list its directory must be listed too.
- `filesystem.protect` (FS-6, K-FS-07): Landlock has no rule that takes a right away beneath a granted directory, so a protected path is kept read-only by a mount (`src/akios/substrate/mounts.py`). Before Landlock, the child enters a new mount namespace, inside the user namespace of `network: none` when there is one, else in a user namespace of its own (its uid and gid mapped to themselves, as in §5.2), and bind-mounts each protected path onto itself, read-only. Writing, truncating or creating beneath it then fails with `EROFS`; renaming, removing or replacing it fails with `EBUSY` (it is a mount point), and making a hard link to it with `EXDEV`. The folders above a protected path whose parent is beneath a `write` directory are bind-mounted onto themselves too, writable, so that they cannot be renamed; renaming a file across such a folder fails with `EXDEV`, as across file systems. The mounts exist only in the run's namespace and do not propagate to the host. The child cannot remove them: after `execve` it has no capability in its user namespace, Landlock denies mount operations to a restricted process, and the baseline filter denies `mount`, `umount2`, `unshare` and `setns` (SYS-1). The clause is unenforceable (§6) where an unprivileged user and mount namespace cannot be made (the probe of `akios doctor`, for example under AppArmor's restriction of unprivileged user namespaces), when a protected path that an existing `write` directory contains does not exist at run start (the child could create it, and a mount needs an existing path), and when a file system is mounted beneath a protected directory. A protected path that no existing `write` directory contains needs no mount: Landlock already denies writing there.

### 5.2 `network`

- `none`: the child runs in a new network namespace (NET-1), entered through an unprivileged user namespace in which its own uid and gid are mapped to themselves (files keep their owner, and the child has no capability after `execve`); its loopback interface is brought up and no route leads out. Kernels with tunnel drivers built in also create their fallback tunnel devices in every new namespace; they stay down, and the child cannot bring them up. Availability is probed by a short-lived child before the decision. If user namespaces are unavailable (for example restricted by AppArmor on Ubuntu 23.10 and later), a seccomp rule makes `socket()` fail for `AF_INET` and `AF_INET6` (NET-2); this is weaker, and the ledger records which mechanism was used. If neither is available, the clause is unenforceable. With a user namespace on Linux 5.14 or later, `RLIMIT_NPROC` counts only the run's tasks, so `max_processes` is applied without the user-wide offset of §5.5.
- `all`: nothing is restricted; the ledger records it.
- `domains` (**experimental**): planned as a local proxy that only connects to the listed domains. Without a network namespace, the child can bypass it by opening sockets directly. In AKIOS 2.0.0 the clause is unenforceable until the proxy exists.

### 5.3 Baseline

Whatever the policy says, the child runs with `PR_SET_NO_NEW_PRIVS` and the baseline seccomp filter (SYS-1), with every file descriptor closed except 0, 1 and 2, and the wrapper makes itself non-dumpable (PROC-1). The baseline is not a clause, but it is part of the enforcement matrix (row `baseline`): where it cannot be applied (hosts other than Linux and macOS, a Linux architecture other than x86_64 or aarch64), the run is unenforceable. On macOS the baseline is part of the Seatbelt profile (§5.7). The filter is generated in classic BPF by `src/akios/substrate/seccomp.py` (no `python3-seccomp`), built by the wrapper, and loaded by the child as its last step before `execve`.

### 5.4 `environment`

The child receives the base set, taken from AKIOS's own environment when present (`PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `TERM`, `TZ`, `TMPDIR`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `TMPPREFIX`), plus the listed names. `SSL_CERT_FILE` and `SSL_CERT_DIR` say where the trusted certificates are: a program that loads its trust settings through the system's security service, which the cage does not reach (on macOS the security server is not among the base services), fails to verify any certificate under the baseline unless it is told where they are; they name files, not secrets. `TMPPREFIX` is where zsh writes its temporary files, here-documents among them. `all` passes the whole environment. Variables not passed are absent from the child (ENV-1); secrets a policy does pass are visible to the child.

Two variables of the base set have a default, which the wrapper sets when the child's environment does not have them, also with `all`: `TMPPREFIX` is `$TMPDIR/zsh` when `TMPDIR` is an absolute path (zsh's own default is `/tmp/zsh`, which a policy that grants `$TMPDIR` does not grant); on macOS, when `network` is not `none`, `SSL_CERT_FILE` is `/etc/ssl/cert.pem`, the system's certificates, which the platform base lets such a run read (§5.7). A program that verifies a certificate through the system, as `curl` does, is not affected. The ledger records the names of the variables the child received, defaults included.

### 5.5 `resources`

| Key | Mechanism | Notes |
|---|---|---|
| `wall_seconds` | wrapper watchdog: `SIGTERM`, then `SIGKILL` after 5 s, to the process group | Linux: a descendant that leaves the process group survives unless a delegated cgroup is used. macOS: the run's processes outside the group are signalled too, and killed at the end of the run (§5.7) |
| `cpu_seconds` | `RLIMIT_CPU`, soft limit the value, hard limit one second more: `SIGXCPU`, then `SIGKILL`. macOS: also the wrapper's CPU sampler | counted per process, not for the whole tree. On macOS, `RLIMIT_CPU` sends `SIGXCPU` once, at the limit, and nothing at the hard limit, so alone it does not stop a process that ignores `SIGXCPU`, nor, on some Macs, one that reads its own CPU time: the wrapper reads the CPU time of each process of the run every 250 ms and ends the run when one reaches the hard limit (the value plus one second). The sampler finds the run's processes by their Seatbelt profile: without it, the clause is unenforceable |
| `memory_mb` | `memory.max` in a delegated cgroup, else `RLIMIT_AS` (Linux) | `RLIMIT_AS` caps address space, not resident memory. `memory_mb` is not enforced on macOS: the clause is unenforceable there (§6), and a policy for macOS omits it or allows a degraded run |
| `max_processes` | `pids.max` in a delegated cgroup, else `RLIMIT_NPROC` | `RLIMIT_NPROC` counts all processes (on Linux, all threads) of the user: the wrapper sets it to that count at start plus the value, and records both; approximate. Unenforceable for root |
| `file_size_mb` | `RLIMIT_FSIZE` | a larger write gets `SIGXFSZ` |

A limit above the host's current hard limit is lowered to it, and the ledger's `enforcement` event says so.

Exceeding a limit ends the run and `akios run` exits with code 124. The ledger records a `budget_exceeded` event with the limit and the measured value: for `wall_seconds`, before the wrapper kills; for `cpu_seconds` and `file_size_mb`, from the signal the kernel sent (`enforced_by: kernel`); on macOS, for `cpu_seconds` stopped by the sampler, before the wrapper kills (`enforced_by: cpu_sampler`, with `sampling_interval_ms`). A failed allocation under `RLIMIT_AS` or a failed `fork` under `RLIMIT_NPROC` cannot be told apart from other errors, so no `budget_exceeded` is recorded for them.

### 5.6 `ledger`

What a run records is defined in the [evidence format](/docs/ledger-v0.html). `argv: redacted` passes the command line through the PII and secret redaction before it is written and hashed. `output_digests: true` makes the wrapper read the child's stdout and stderr through pipes, so the child no longer writes to a terminal; interactive programs need `false`.

`denials: true` (the default) records, at the end of the run, a bounded summary of the operations the cage refused: the `denials` event of the [evidence format](/docs/ledger-v0.html#3-events), and `akios run` names them in one line, whatever the exit code, and `akios report` lists them. On macOS they come from the reports the sandbox writes to the system log (§5.7, M-SYS-02). On Linux, Landlock and seccomp do not report their refusals by default; nothing is captured, and the report says so ([threat model §8](/docs/threat-model.html#8-known-limitations-of-the-20-design)). `false` reads nothing and records no `denials` event; on macOS it saves the one reader process per run.

### 5.7 macOS (Seatbelt)

On macOS, `baseline`, `filesystem`, `exec` and `network` are enforced by one Seatbelt profile per run, without root and without an entitlement. The wrapper builds it from the effective policy; the child applies it with `sandbox_init_with_parameters` between `fork` and `execve`, and the ledger records the clauses as applied only once that call has returned. The profile is inherited by every descendant and cannot be lifted or replaced. Each path enters the profile as a parameter, never as profile text. The properties and their tests are in [threat model §5a](/docs/threat-model.html#5a-what-each-mechanism-enforces-macos).

- **Resolved paths.** Rules match resolved paths. `/tmp`, `/var` and `/etc` are links to `/private/tmp`, `/private/var` and `/private/etc`, and are granted in that form (§4.2). Most programs write their temporary files to the per-user `$TMPDIR` (beneath `/private/var/folders`), not to `/tmp`; a policy grants it with the `$TMPDIR` path (§4.1).
- **Platform base, version 4.** Read-only, granted to every run without being declared, and printed by `akios policy explain`: the directories `/System`, `/usr/lib`, `/usr/share`, `/Library/Apple`, `/private/var/db/timezone`, `/private/var/db/dyld`, and the files `/`, `/dev/null`, `/dev/zero`, `/dev/random`, `/dev/urandom`, `/dev/autofs_nowait`, `/dev/dtracehelper`, `/private/etc/localtime`, `/private/etc/passwd`, `/private/etc/group`, `/private/etc/protocols`, `/private/etc/services`, `/private/var/db/xcode_select_link`, `/Library/Preferences/.GlobalPreferences.plist`, `/Library/Preferences/com.apple.security.plist`, and `xcrun_db` in the per-user temporary folder (the folder `confstr(_CS_DARWIN_USER_TEMP_DIR)` gives, which `$TMPDIR` names by default; the folder itself is not granted); with `network: all`, also `/Library/Preferences/com.apple.networkd.plist`, `/private/etc/ssl/cert.pem` (the system's certificates) and `/private/etc/ssl/openssl.cnf` (the configuration of the system's TLS library, which `curl` reads at start). Two denials that nearly every program meets at start, and does without, are not reported to the system log; they stay denied: writing `/dev/dtracehelper` and reading `/Library/Preferences/Logging/com.apple.diagnosticd.filter.plist`. Writing is allowed to `/dev/null`, `/dev/zero` and `/dev/fd`. These hold the system's libraries, special files and system-wide preferences (the ones in `/Library/Preferences` apply to every user of the Mac), and the paths of the developer tools, no user data. Version 2 added `/dev/dtracehelper`, which the dynamic loader opens at every start, and the three preference files, which the system libraries read for programs such as `git`; version 3 added `xcrun_db`, the lookup cache of the developer tools of `/usr/bin` (below); version 4 added, with network, the two files of `/private/etc/ssl` a TLS client reads (M-NET-03). The security server, which also serves the keychains, stays outside the base.
- **`filesystem`.** As in §5.1: `read` grants reading and listing, `write` grants reading, creating, writing, truncating, renaming, linking and deleting. A denied operation fails with `EPERM` ("Operation not permitted"), where Landlock returns `EACCES`. As with Landlock, `stat()` succeeds on any path: existence, size and dates are visible, contents and listings are not.
- **`exec`.** `exec: any` grants execution beneath every `read` and `write` path. An `exec` list grants reading and execution beneath the listed paths only. A script's `#!` interpreter is checked too and must be listed, and a symbolic link is checked at its target: `/opt/homebrew/bin/python3` is a link into `/opt/homebrew/Cellar`.
- **setuid and setgid programs** never start: macOS refuses them to a sandboxed process, and the profile refuses them too. `ps`, `top` and `pgrep` do not work inside the cage.
- **Privacy-guarded folders.** `~/Desktop`, `~/Documents`, `~/Downloads` and `~/Library/Mobile Documents` (iCloud Drive) are granted only when the policy lists the folder itself, or a path inside it. A policy that would grant one only through a broader path, such as `~/Library`, has no profile: its `baseline`, `filesystem`, `exec` and `network` clauses are unenforceable (§6). When a policy lists such a folder, macOS may ask, on behalf of the terminal application, or deny access without asking.
- **`network`.** `none`: no IP traffic and no name resolution, loopback included; a program that runs its own local server needs `network: all`. `all`: IP traffic, name resolution and certificate checks; a connection to a kernel control socket (`AF_SYSTEM`, which some system libraries open for network statistics) stays denied, and the system log names that refusal without an address (M-NET-02). In both modes, a Unix-domain socket can be created or connected to only beneath a `filesystem.write` directory; the Linux substrate has no such rule. `domains` has no rule: when the run is allowed to start degraded, the profile applies `all`, and the ledger's `baseline` detail says so.
- **The run's terminal.** When the run's stdin is a terminal whose foreground process group is the wrapper's, the profile also allows `/dev/tty` and that terminal device; no other terminal device can be opened.
- **Baseline.** Deny by default; six Mach services (user and group lookups, group membership, notifications, logging, and `com.apple.bsd.dirhelper`, which gives a process its per-user temporary and cache folders; with `network: all`, also name resolution, certificate checks and network configuration). Group membership and `dirhelper` hold no user data, and every `git` call asks for both; signals only to processes of the same sandbox; no second sandbox; file descriptors above 2 closed. Other processes of the same user can read each other's initial environment on macOS; AKIOS overwrites the unpassed values in its own, before the fork.
- **The policy file** of the run is read-only in the cage, also inside a granted directory: writing, truncating, replacing, linking, renaming or deleting it fails, and so does renaming or removing a folder above it that a `write` path contains (it could otherwise be moved aside, changed and moved back). Reading it works. Passed through a symbolic link outside the write paths, the file the link leads to is the one kept read-only; a link inside them is rejected (§4.6) (M-FS-06). On Linux, Landlock has no rule that takes one file out of a granted directory: a program can rewrite a policy file kept beneath a `write` path unless the policy lists it in `filesystem.protect` ([threat model §8](/docs/threat-model.html#8-known-limitations-of-the-20-design)).
- **`filesystem.protect`** (M-FS-07): each protected path is denied for writing by a rule placed after every grant (the last matching rule wins in a profile), so it holds inside a `write` directory: writing, truncating, creating, replacing, linking, renaming or deleting it fails with `EPERM`, a directory with everything beneath it, and a path that does not exist cannot be created; the folders above it that a `write` path contains cannot be renamed or removed. Reading works.
- **Denials** (M-SYS-02): every rule of the profile that denies and reports carries the run's marker (§5.7, "The run's processes") as its message, so each report the sandbox writes to the system log for the run, from any of its processes, ends with that marker. With `ledger.denials`, the wrapper reads these reports with one `/usr/bin/log stream` process, filtered on the kernel's sandbox reports that carry the marker. Before the command starts, it waits until the reader has received a report it caused itself (a beacon: a process of the wrapper, outside the run, kept until the run ends, whose own profile denies a lookup with a report); the wait is usually about 20 ms (up to half a second was seen), at most 2 s, after which the run starts anyway and the record says it may miss the first denials. Once the run's processes are gone, it waits in the same way for the beacon's end report, then 0.5 s more when something was refused, for the repeats macOS folds into one report it writes later. The two denials the platform base keeps out of the log, and AKIOS's own checks of the run's processes, are not reported, so not recorded. macOS folds repeated reports and can drop reports when many are written at once, so a count is what the log delivered. The record keeps first a write refused on a path the profile keeps read-only (`filesystem.protect`, the policy file), then every refused write and execution, then the most frequent of the others, reads grouped by folder when they do not fit ([evidence format §3](/docs/ledger-v0.html#3-events)). The reader costs one process per run, about 6 MB of memory and a few hundredths of a second of CPU time at start.
- **Reserved paths** are denied by the last rules of the profile, so they stay unreachable even inside a granted directory; validation still rejects a policy that grants them (§4.4).
- **The run's processes** all carry the profile, which lets the wrapper find them, also those that left the process group: they are signalled after a wall-clock kill and when the wrapper is interrupted, and killed at the end of the run (the process sweep), which the ledger records as `process_sweep` with the number found and ended.
- **Resources.** `wall_seconds`, `cpu_seconds`, `max_processes` and `file_size_mb` as in §5.5, with the CPU sampler for `cpu_seconds`. `memory_mb` is not enforced on macOS.
- **A policy for macOS.** [`coding-agent-macos.policy.yaml`](https://github.com/akios-ai/akios/blob/main/docs/spec/examples/coding-agent-macos.policy.yaml) grants Homebrew, the developer tools (`$DEVELOPER_DIR`), the project for reading and `$TMPDIR` for writing, and has no `memory_mb`; on macOS, `akios init` writes a starter of the same shape from what it finds.
- **The developer tools of `/usr/bin`.** `/usr/bin/python3`, `git`, `make`, `clang` and the other developer tools in `/usr/bin` are shims: each asks `xcrun` for the tool of its name in the selected developer tools (`xcode-select -p`), then runs it with the variables `xcrun` sets (`SDKROOT`, `CPATH`, `LIBRARY_PATH`, `MANPATH`). `xcrun` finds the tool in its lookup cache, `xcrun_db`; when the cache does not hold it (after the developer tools are installed or updated, for example) and the developer tools are Xcode, it looks it up with `xcodebuild`, which needs Xcode's frameworks and settings and cannot start inside the cage, and then writes the cache. So, before the run and outside the cage, `akios run` asks `xcrun --find`, with the environment the run will have, for each shim the command check meets (the program, or the program a `#!` line runs); `xcrun` writes the answer in its cache, and the platform base lets the shim read that one file in the cage, where it then finds its tool and runs it as it does outside, with the same variables, writing nothing (M-SYS-01 checks that a run reads that file and cannot list its folder; `test_a_shim_of_usr_bin_starts_in_the_cage_with_a_cold_lookup_cache` runs `/usr/bin/python3` with a cache that did not hold it). The command runs as given and the policy needs no other path: the `decision` event records each shim with the tool `xcrun` found ([evidence format §3](/docs/ledger-v0.html#3-events)), and `akios policy explain --command` prints it. Running the tool `xcrun` finds in place of the shim would leave out those variables (`clang` would not find the SDK's headers), and granting the cache's folder for writing would grant the whole per-user temporary folder and still leave `xcodebuild` denied. A developer tool the program starts later through a shim is found in the same cache when the cache holds it; otherwise it fails as above, and `xcrun --find <tool>`, run once outside the cage, puts it there. The shims also load `xcrun`'s library from the developer tools, which a policy grants with `$DEVELOPER_DIR` (§4.1); without it, a shim fails in the cage with `xcrun: error: unable to load libxcrun`. When the policy expects developer tools (it grants git's configuration, `~/.gitconfig` or `~/.config/git`, or a folder of developer tools), the first `git`, `python3`, `make` or `clang` on the run's `PATH` is a shim the cage lets run, and that folder cannot be read under the policy, `akios run` and `akios policy explain --command` print one line before the run that names the folder (`test_a_note_when_the_shims_on_path_load_developer_tools_the_policy_does_not_grant`); it refuses nothing.
- **Availability.** `akios doctor`, `akios policy explain` and `akios run` apply a two-rule profile in a short-lived child and check that it denies a write; if not, the four clauses are unenforceable (§6).

## 6. Clauses that cannot be enforced

Before starting the child, AKIOS computes, for each clause, whether this host can enforce it. If one cannot:

- with `on_unenforceable: refuse` (the default), the run does not start and `akios run` exits with code 3;
- with `on_unenforceable: degrade`, or `--allow-degraded` on the command line, the run starts and the ledger records a `degraded` event, before the child starts, listing the clauses not enforced.

A clause with nothing to enforce (`network: all`, an absent `resources` key) is never unenforceable. The full rules are in [threat model §6](/docs/threat-model.html#6-fail-closed-rules).

### 6.1 The command check

When the filesystem clause will be enforced, `akios run` also resolves the command as the system will run it, before the child starts, and checks that each file it needs before its first instruction is granted:

- the program: looked up in `PATH` when its name has no slash, then followed to its target when it is a symbolic link; on macOS, for a shim of `/usr/bin` (`/usr/bin/python3`, `git`, `make`, `clang`), the developer tool it runs, as `xcrun --find` names it before the run (§5.7);
- the `#!` interpreter of a script, `/usr/bin/env NAME` looked up in `PATH`, for up to four levels; on Linux, the ELF program interpreter (the dynamic loader);
- for a Python interpreter: the `pyvenv.cfg` of its virtual environment, the standard library of the installation it runs from, the script it is given, and on macOS, before Python 3.14, the working directory when it runs `-c`, `-` or interactively without `-I` or `-P` (Python looks up modules there first, which needs read access on macOS).

A file that is executed must be beneath an `exec` path (a list), or beneath a `read` or `write` path (`exec: any`); a file that is read, beneath a `read`, `write` or `exec` path, or on macOS the platform base (§5.7). If a file is not, the run is refused (exit code 3), and one message names every such file the check can determine (the program, each `#!` interpreter, the developer tools, the virtual environment and the installation it was created from, the script, the working directory), each with the path to add (its installation folder, such as the Homebrew prefix, a framework or the folder above `bin`, never a reserved path or a folder above one) and the clause (`filesystem.read`, or `exec` with a list). The ledger records the refusal in the `decision` event ([evidence format §3](/docs/ledger-v0.html#3-events)). `akios policy explain --command` runs the same check. The check grants nothing; it only says, before the run, what the system would deny. Shared libraries, data files and what the program opens later are not checked.

## 7. Validation

A policy is valid when it passes the schema and:

1. no resolved path is, or contains, a reserved path (§4.4);
2. every path of `filesystem.protect` lies strictly inside a `filesystem.write` path (§4.5);
3. neither the policy file nor a path of `filesystem.protect` is named through a symbolic link inside a `filesystem.write` path (§4.6);
4. `network_domains` appears exactly when `network` is `domains`;
5. its YAML has no duplicate keys, tags, anchors, aliases or merge keys (`<<`), no non-string keys, no fractional numbers and no unquoted dates (YAML 1.1 would read `2026-09-29` as a date); a file whose name ends in `.json` is parsed as JSON with the same restrictions.

`akios policy validate` reports each error with its location (a JSON pointer). `akios policy explain` prints, for this host, how each clause would be enforced, which clauses are required, and whether `akios run` would start, start degraded, or refuse. `akios policy test <file>` applies the PII and secret redaction that AKIOS uses on what it records to a sample file.

## 8. Effective policy

The effective policy is the validated document with defaults filled in and every path in both its declared and resolved form. It is written to the export bundle as `policy.json` in canonical JSON, and its SHA-256 digest is recorded in the first ledger event, so the signature over the ledger covers the policy (see [evidence format §3](/docs/ledger-v0.html#3-events)). It is exported exactly as it was enforced, without redaction: names, description and paths appear in `policy.json` and in `akios report` as they are in the policy file.
