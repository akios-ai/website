## 1. What is protected

AKIOS wraps one process, the *child*, and all its descendants for one run. It applies a declared policy to them and writes a ledger of the run.

| Asset | What an attack looks like |
|---|---|
| Host files outside the policy | reading `~/.ssh`, `~/.aws` or a browser profile; writing or deleting outside the project |
| Credentials | secrets in those files, or in environment variables handed to the child |
| Network | exfiltration, reaching internal services, downloading a payload |
| Budget | CPU time, memory, wall time, processes or disk consumed without limit |
| Evidence | a ledger edited, truncated, reordered or replaced so that it misstates what the child did |

## 2. Adversaries

The child is treated as hostile from its first instruction:

- **A1, buggy agent.** Well-meant code that runs a destructive command, loops, or leaks a file by mistake.
- **A2, prompt-injected agent.** An agent whose next action is chosen by content it read (a web page, an issue, a file). It can run any command the agent can run.
- **A3, malicious dependency.** Arbitrary native code inside the wrapped process that knows how AKIOS works and tries to escape, exfiltrate, or falsify the evidence.

A1 to A3 have the same capability: arbitrary code execution as the invoking user, inside the child's process tree, from the start of the run. AKIOS does not rely on the child cooperating, on its language runtime, or on hooks inside it.

- **A4, evidence tamperer.** Anyone who handles an exported bundle, at rest or in transit, and wants it to say something else. A4 does not hold the signing key.

## 3. Out of scope

- Kernel exploits, and bugs in the kernel mechanisms AKIOS uses. The kernel is trusted.
- Root, or any process with capabilities on the host, including a malicious local administrator.
- Other processes of the invoking user **outside** the cage. They can read the signing key and edit the ledger store; the user's own session is trusted.
- Hardware side channels, timing and covert channels.
- The content of TLS traffic: with `network: all`, AKIOS 2.0 does not see or redact what the child sends.
- Whether the agent's work inside its allowed scope is correct: an allowed write can still be a bad write.
- Denial of service against the host beyond the resource limits of §5.
- The integrity of the AKIOS installation itself (package supply chain).

## 4. Trust boundaries

```
invoking user ──► akios (wrapper, trusted) ──fork──► apply enforcement ──execve──► child + descendants (untrusted)
                      │ writes                                                         ╳ no access
                      ▼
              ledger store, signing key ──export──► verifier on any machine (trusts only a pinned public key)
```

- **B1, wrapper to child.** The wrapper forks. In the child, before `execve`, it closes every file descriptor except 0, 1 and 2, sets `PR_SET_NO_NEW_PRIVS`, applies the enforcement of §5, then executes the command. The enforcement is inherited by every descendant and cannot be removed by it. The wrapper makes itself non-dumpable (`PR_SET_DUMPABLE 0`), so a same-user child cannot read its memory through `/proc/<pid>/mem`. On macOS the child closes the same descriptors and applies one Seatbelt profile instead of the Linux calls (§5a).
- **B2, child to evidence.** Only the wrapper writes the ledger. The ledger directory and the key directory are *reserved paths*: the child gets no access to them, and a policy that grants any path containing them is rejected. Landlock cannot carve an exception inside an allowed directory, so refusal is the only safe rule. On macOS the profile also denies them after every grant (§5a).
- **B3, host to verifier.** `akios verify` runs on any OS and trusts only the bundle and a public key obtained separately (pinned). Without a pinned key, a valid result means "unchanged since it was signed by the key shipped in this bundle", not "produced by a given machine".
- **B4, kernel.** Trusted (§3).

## 6. Fail-closed rules

1. Before the child starts, the wrapper decides for each policy clause whether this host can enforce it (mechanism present, kernel ABI sufficient). `akios policy explain` and `akios doctor` print the same matrix.
2. If a clause cannot be enforced, `akios run` does not start the child and exits with code 3, naming what is missing. A partial enforcement counts as not enforced.
3. With `--allow-degraded`, or `on_unenforceable: degrade` in the policy, the run starts, and the ledger records a `degraded` event listing the clauses not enforced **before** the child starts. `akios verify` and `akios report` show it.
4. An enforcement is recorded as applied only after the kernel call that applies it returned success. The evidence never states an enforcement that did not happen.
5. If applying a clause fails in the child after the fork, the child exits before `execve` and the run is recorded as refused, even with `--allow-degraded`. Degradation is decided before the fork, never after a failed call.
6. A run with an unenforced `filesystem` clause leaves the reserved paths reachable: the child may read the signing key and forge evidence. The evidence of such a run is untrusted, and `verify` says so.
7. If the wrapper itself fails while the command runs (a ledger write fails, an error while it waits, a step that fails right after the command is forked, such as the start of the macOS denials reader), it kills the run's processes (the child's process group, and on macOS the run's other processes) and reaps the child before it exits, with or without the macOS profile, and gives the terminal back; it then records the error and the child's status if the ledger can still be written, and otherwise the run fails verification as incomplete (EV-3) (R-WRAP-01, R-WRAP-02). The run's processes are the wrapper's to stop from the moment the command is forked, before any other step.
8. With `ledger.output_digests`, the wrapper waits at most 5 seconds after the command ended for the end of its output. A stream still open then is recorded as incomplete, without a digest, and the run ends with its final checkpoint (R-OUT-01).

| ID | Property | Test |
|---|---|---|
| EV-1 | Editing, inserting, deleting, reordering or truncating ledger events after they were signed makes `verify` fail | V-TAMPER-01 to 07 (the seven scenarios of [ledger-v0 §7](/docs/ledger-v0.html#7-tamper-scenarios)) |
| EV-2 | A missing, removed, reordered or unsigned checkpoint makes `verify` fail; the last checkpoint must be the final one | V-CP-01, V-CP-02 |
| EV-3 | A run that ended without a final checkpoint (crash, killed wrapper) fails verification as incomplete | V-CP-03 |
| EV-4 | With a pinned key, a bundle re-signed with another key fails | V-KEY-01 |

| EV-6 | Strings the ledger records (command line, environment variable names, working directory, policy name, error messages) are redacted before they are hashed and signed; the exported effective policy is exact ([ledger v0 §3](/docs/ledger-v0.html#3-events)); on the command line, the value of an option, an assignment or a header whose name marks a credential is masked, also when the option and its value are two arguments and when another option comes before it | R-RED-01, R-RED-02 |

A valid result does not show which machine produced the run, that its clock was right, that the wrapper itself was intact, or anything the ledger does not record.

The formal model [`docs/tla/AKIOSRun.tla`](https://github.com/akios-ai/akios/blob/main/docs/tla/README.md) states EV-1 to EV-3 and rules 2 to 4 of §6 as invariants. It has not been model-checked yet.

## 8. Known limitations of the 2.0 design

- **Enforcement on Linux (§5) and macOS (§5a).** Elsewhere, `run` refuses unless degraded; `verify` and `report` have no platform check.
- **Network is `none` or `all`**. An experimental domain allowlist would go through a local proxy, which the child can bypass without a network namespace. On macOS it needs the same local proxy (planned).
- **Redaction covers what AKIOS records and exports**, not what the child sends. It is heuristic: a secret in a format it does not know, in a position it does not recognise, is recorded as it is ([ledger v0 §3](/docs/ledger-v0.html#3-events)).
- **The key is per installation**, readable by the invoking user, and not bound to hardware or to an identity.
- **Signals (Linux).** Below Linux 6.12 (Landlock ABI 6 scopes signals, PROC-2), a same-user child can kill the wrapper; K-PROC-02 checks both sides. The enforcement stays in place, but the run ends without a final checkpoint and fails verification (EV-3).
- **Resource precision.** `RLIMIT_NPROC` counts every process of the user, not only this run's, and `RLIMIT_AS` caps address space rather than resident memory; runtimes that reserve large address ranges need generous limits. Precise accounting needs a delegated cgroup.
- **Process groups (Linux).** Without a delegated cgroup, a descendant that calls `setsid()` leaves the process group and survives the wall-clock kill, and it can keep the output pipes open: the capture is then recorded as incomplete (§6, rule 8). On macOS the process sweep kills it (M-PROC-02).
- **Network fallback (Linux).** Where unprivileged user namespaces are unavailable, `network: none` is applied as `network: seccomp` (NET-2): IPv4 and IPv6 sockets are refused, and Unix-domain sockets to local services still work; the ledger records the mechanism.
- **File metadata.** On both systems `stat()` succeeds on any path: the existence, size and dates of a file outside the policy are visible, its contents and a folder's listing are not ([policy v0 §5.7](/docs/policy-v0.html#57-macos-seatbelt)).
- **What a valid bundle shows.** That it is unchanged since it was signed with that key; not which machine produced the run, that its clock was right, that the wrapper itself was intact, or anything the ledger does not record (§7, B3). The formal model of the run lifecycle has not been model-checked yet (§7).
- **Nested sandboxes (Linux).** Tools that build their own sandbox with mount namespaces (bubblewrap, some browsers) cannot do so inside the cage, because Landlock forbids mount operations to a restricted process.
- **macOS: memory.** `memory_mb` is not enforced on macOS. The clause is unenforceable there: a policy that sets it is refused unless the run is degraded, and the ledger records it.
- **macOS: environments of other processes.** Other processes of the same user can read each other's initial environment on macOS; AKIOS overwrites the unpassed values in its own (M-PROC-01).
- **macOS: no private loopback.** With `network: none`, loopback is denied too; a program that runs its own local server needs `network: all`. `network: domains` is applied as `network: all` when the run is allowed to start degraded, and the ledger says so.
- **macOS: CPU time.** `RLIMIT_CPU` sends `SIGXCPU` once, at the limit, and nothing at the hard limit: a process that ignores `SIGXCPU` keeps running, and on some Macs so does one that reads its own CPU time (on the Mac of the local runs it does; on the `macos-latest` CI image the kernel stops it). The wrapper's CPU sampler stops such a process; it reads the run's CPU times every 250 ms, so the process can exceed the hard limit (the value plus one second) by up to one interval of CPU time per running thread.
- **macOS: process count.** `RLIMIT_NPROC` counts every process of the user, as on Linux without a user namespace; on a desktop that count moves as other applications start and stop.
- **macOS: process-listing tools.** `ps`, `top` and `pgrep` do not work inside the cage.
- **macOS: nested sandboxes.** A program that applies its own Seatbelt profile (`sandbox-exec`, some build tools and browsers) cannot do so inside the cage (M-SYS-01).
- **macOS: the Keychain and the developer tools.** The security server, which also serves the keychains, is out of reach in the cage: a sign-in an agent keeps in the Keychain is not available there. With Xcode as the developer tools, a developer tool a program starts later through a shim of `/usr/bin` runs only when `xcrun`'s lookup cache already holds it ([policy v0 §5.7](/docs/policy-v0.html#57-macos-seatbelt)).
- **macOS: privacy-guarded folders.** Desktop, Documents, Downloads and iCloud Drive are granted only when the policy lists them; macOS may then ask, on behalf of the terminal application, or deny access without asking.
- **The policy file (Linux).** Landlock grants whole hierarchies and has no rule that denies: it cannot take one file out of a directory the policy grants for writing. A program can rewrite a policy file kept in such a directory (the starter policy of `akios init` is in the project, which it grants for writing), and the next run applies what it wrote. `run_start` records the SHA-256 of the policy file, and `akios run` prints one line when the file changed since the previous run with it in the same ledger store. List the policy file in `filesystem.protect` (FS-6, K-FS-07), or keep it outside the write paths and pass it with `--policy`, when the program must not change it. On macOS the profile makes it read-only (M-FS-06). On both systems, a policy file named through a symbolic link inside a write path is refused: the program could replace the link ([policy v0 §4.6](/docs/policy-v0.html#4-paths)).
- **Configuration that runs later, outside the cage.** A write grant lets the program leave files that something else runs later. Granting write on an agent's own configuration folder lets the agent change its settings, hooks, allow lists or the commands it starts: the next time the agent is started without AKIOS, those changes run outside the cage, with the user's full access, and AKIOS records nothing about them. `filesystem.protect` keeps chosen paths of a write grant read-only (M-FS-07, K-FS-07): the agent keeps writing its state while its configuration stays as it was. AKIOS cannot know which files of an agent run later: the policy names them, and what it does not name stays writable. Otherwise grant such a folder for reading, or grant write on the narrowest path the agent needs (its cache or session folder), and review what changed there before running the agent outside the cage.
- **Protected paths.** The rules match paths: a hard link to a protected file made before the run, elsewhere in a write grant, is a second name for the same file, and writing through it works; the cage refuses new links (M-FS-07, K-FS-07, each with a test of this limit). For the same reason, a protected path named through a symbolic link inside a write path is refused ([policy v0 §4.6](/docs/policy-v0.html#4-paths)): the cage would keep the file the link leads to, not the link. On Linux, a protected path must exist at run start when an existing write directory contains it, or the clause is unenforceable (the child could create it, and a mount needs an existing path); a protected directory with a file system mounted beneath it is unenforceable too; and renaming a file across a folder kept in place fails with `EXDEV`, as across file systems, which a program that renames into place handles or reports. On macOS a protected path that does not exist cannot be created.
- **Denials (Linux).** Landlock and seccomp do not report their refusals by default: on Linux `akios report` says `Denials: not captured (on Linux, Landlock and seccomp refusals are not logged by default; a capture is planned. …)` (`tests/unit/test_ledger/test_report.py`), and the program's output shows them ("Permission denied", `EACCES`, or "Operation not permitted", `EPERM`). A capture is planned. Landlock writes audit records of its denials from Linux 6.15 (ABI 7), and seccomp can log the calls its filter denies (`SECCOMP_FILTER_FLAG_LOG`, `SECCOMP_RET_LOG`), but both go to the audit log or the kernel log, which an unprivileged process often cannot read (`CAP_AUDIT_READ`, `kernel.dmesg_restrict`), and AKIOS needs no root. The design considered: count the baseline's refusals in the wrapper through a seccomp user-notification filter (`SECCOMP_RET_USER_NOTIF`, Linux 5.0), which needs no privilege, read Landlock's records where the host lets the user read them, and record "not captured" with the reason otherwise; each source with its own test before it is claimed.
- **macOS: denials.** The record comes from the system log, not from the kernel's decisions: macOS folds repeated reports into one it writes later and can drop reports when many are written at once, so a count is a lower bound, and folded repeats written more than half a second after the run's end are not counted. The reader is confirmed attached before the command starts (usually after about 20 ms); if it is not within 2 s, the run starts anyway and the record says that denials at the start can be missing. A program can make the record incomplete by being refused many different things: every refused write on a protected path is recorded, then every refused write and execution (100 entries, grouped by folder beyond), then the 25 most frequent of the others, reads grouped by folder; what does not fit is counted per operation, of at most 4096 pairs of each kind counted. The two denials the profile keeps out of the log are never recorded. Each run starts one `/usr/bin/log` process (about 6 MB of memory and a few hundredths of a second of CPU time at start); `ledger.denials: false` turns it off. macOS keeps much of its `log` command to administrators (`/usr/bin/log` holds the message `Must be admin to run '%s' command`): for a standard account the reader either refuses, and the record gives its message, or, as reported for some versions, runs and delivers nothing; either way nothing is captured, the run goes on, and `akios report` says `Denials: not captured (the system log delivered nothing for this run: …)` with the reason. A standard account was not tested; the unit tests fake both cases (M-SYS-02).
- **Release artefacts.** A released wheel names the git tree of its release commit (`akios --version`, `akios_source_tree` in `run_start`) and is reproducible from that commit; the sdist is not reproducible, and the SHA-256 of both is recorded per release ([release procedure](https://github.com/akios-ai/akios/blob/main/tools/release/RELEASE_PROCESS.md#identifying-a-release)). Any other installation records `akios_source_tree: null`.

## 9. What 2.0 changes compared with 1.x

| | AKIOS 1.x | AKIOS 2.0 |
|---|---|---|
| What runs | YAML workflows, executed by built-in agents and model clients | Any program, wrapped with `akios run -- <command>` |
| Where the policy is enforced | In the built-in agents, inside the AKIOS process | By the kernel, on the wrapped program and all its descendants, without root (§5) |
| What is recorded | Workflow events in an audit log | One ledger per run: the decision before the start, the enforcement of each clause, the outcome (§7) |
| How the record is checked | A hash per event and a Merkle root file stored next to the log | A hash chain over every field and Ed25519-signed checkpoints, checked by `akios verify`, with an optional pinned key (§7) |
| Formal model | A model of the 1.x enforcement | A model of the 2.0 run lifecycle ([`AKIOSRun.tla`](https://github.com/akios-ai/akios/blob/main/docs/tla/README.md)) |

AKIOS 1.x is no longer maintained; the [migration guide](/docs/migration-1x-to-2.html) shows how to move to 2.0.
